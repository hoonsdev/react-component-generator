# TDD Rule

**이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 단계를 건너뛰거나 순서를 바꾸거나 "이번만 예외"를 만들지 않는다.

## 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그 규칙이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 없거나 침묵하는 부분에만 적용한다.

## 적용 기준

### TDD 필수

- **비즈니스 로직**: 조건 분기, 계산, 상태 전이
- **API**: 핸들러, 요청/응답 처리, 에러 매핑
- **유틸 / 순수 함수**: 변환, 파싱, 포맷팅
- **버그 수정**: 먼저 버그를 재현하는 실패 테스트를 작성한 뒤 고친다
- **동작이 있는 훅 / 컴포넌트 로직**: 사용자 입력에 따라 결과가 달라지는 것

### TDD 불필요

- **타입 정의** (`type`, `interface`)
- **설정 파일** (tsconfig, vite config, eslint config 등)
- **순수 UI**: 로직 없는 마크업과 스타일
- **SQL / 마이그레이션 스크립트**

판단이 애매하면 **TDD를 적용한다.**

## RED-GREEN-REFACTOR

### 1. RED: 실패하는 테스트 작성

- **하나의 동작 = 하나의 테스트.** 한 테스트에 여러 동작을 섞지 않는다.
- 테스트 이름은 기대 동작을 서술한다.
- **반드시 실행해서 실패를 확인한다.** 실행 없이 실패했다고 가정하지 않는다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. import 오류, 문법 오류, 오타로 인한 실패는 RED가 아니다. 테스트를 고쳐 올바른 이유로 실패시킨다.

### 2. GREEN: 최소한의 코드

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI**: 지금 테스트가 요구하지 않는 기능, 옵션, 분기를 추가하지 않는다.
- 실행해서 **신규 테스트와 기존 테스트가 모두 통과**하는지 확인한다.

### 3. REFACTOR: 정리

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **테스트는 계속 green이어야 한다.** 수정할 때마다 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 4. 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 테스트로 덮일 때까지 반복한다.

## 삭제 강제 규칙

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 그 코드를 삭제하고 RED부터 다시 시작한다.**
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 기억해서 다시 쓰기 모두 포함한다.
- 삭제 후에는 테스트 먼저, 구현은 테스트가 요구하는 만큼만 새로 작성한다.

## 변명 차단표

| 변명 | 반론 |
|---|---|
| 너무 단순해서 테스트 불필요 | 단순한 코드는 테스트도 단순하다. 비용이 거의 없고, 나중에 복잡해질 때 회귀를 막아준다. |
| 나중에 추가하겠다 | 나중에 쓴 테스트는 구현에 맞춰 작성되어 버그를 놓친다. 실제로 "나중"은 오지 않는다. |
| 시간이 없다 | 테스트 없는 코드의 디버깅과 재작업이 더 오래 걸린다. 급할수록 RED-GREEN을 지켜라. |
| 삭제하면 낭비다 | 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 다시 쓰는 비용보다 크다. |
| 프로토타입이다 | 프로토타입은 프로덕션이 된다. 테스트 없이 시작한 코드는 버려지지 않는다. |
