# commit

변경사항을 분석해 컨벤션에 맞는 한국어 커밋 메시지로 커밋한다. 별도 승인 절차 없이 바로 커밋한다.

## 사전 확인

- `git rev-parse --is-inside-work-tree`로 git 저장소인지 확인한다. 저장소가 아니면 커밋하지 말고 그 사실을 알리고 `git init` 여부를 묻는다.
- 현재 브랜치가 기본 브랜치(main/master)면 새 브랜치를 만들지 먼저 묻는다.

## 절차

### 1. 변경사항 분석

- `git status --short`로 변경 파일 목록을 확인한다.
- `git diff`(unstaged)와 `git diff --staged`(staged)를 모두 읽고, 새 파일(untracked)은 내용을 직접 읽는다.
- `.env`, 키·토큰 같은 비밀 정보, `node_modules`, `dist`, 빌드 산출물이 변경에 섞여 있으면 커밋 대상에서 빼고 알린다.

### 2. 논리적 단위로 분류

- 한 커밋은 한 가지 목적만 담는다. 서로 다른 목적의 변경은 커밋을 나눈다.
- 분류 기준:
  - `feat`: 사용자에게 보이는 새 기능이나 화면 추가
  - `fix`: 버그 수정
  - `refactor`: 동작 변경 없는 구조·코드 개선
  - `chore`: 설정, 의존성, 빌드, 문서, 스킬 파일 등 그 외
- 테스트는 대상 코드와 같은 커밋에 둔다. 한 파일 안에서 목적이 섞였다면 `git add -p`로 나누는 방안을 제안한다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문(선택)>

Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>
```

- 요약은 한국어, 명령형이 아닌 간결한 서술(예: `feat: 프롬프트 입력창에 예시 선택 기능 추가`), 50자 안팎, 마침표 없음.
- 본문은 "무엇을"보다 "왜"를 적는다. 요약만으로 충분하면 생략한다.
- type 뒤에는 콜론과 공백을 붙인다. 영문 type 외 코드 식별자·기술 용어는 원문 그대로 쓴다.
- 마지막 줄에 위 `Co-Authored-By` 줄을 둔다. 세션 시스템 알림이 다른 attribution을 지정하면 그것을 따른다.

### 4. 커밋

- 승인을 기다리지 않고 바로 커밋한다.
- 파일을 이름으로 지정해 stage한다(`git add -A`, `git add .` 금지). 커밋이 여러 개면 순서대로 실행한다.
- 메시지는 heredoc으로 전달해 줄바꿈을 보존한다.
- hook이 실패하면 `--no-verify`로 우회하지 말고 원인을 고쳐 새 커밋을 만든다. 직전 커밋을 `--amend`하지 않는다.
- 끝나면 `git log --oneline -n <커밋 수>`로 커밋별 포함 파일과 메시지를 요약해 보고한다. 푸시는 사용자가 요청할 때만 한다.
